MuseStack：StackChan × Muse 开发计划
版本：0.1｜日期：2026-10-19（Asia/Shanghai）｜状态：设计草案，尚未实机验证
1. 项目目标与结论
把用户手上的 StackChan 变成其现有 Muse Agent 的实体交互终端：能听、能说、显示表情、转头注视、接收触摸，并最终播报 Muse 的任务进展。Muse 继续承担推理、个人上下文和工具执行；固件承担低延迟交互和硬件控制。项目暂名 MuseStack，避免与上游 MuseChan 混淆。
推荐从 Tjtelenda/musechan 派生，使用官方 Muse Gadget SDK 接入；借鉴 Groki Bot 的交互、调度和动作设计。不要先重写硬件驱动，也不要把 Grok 的私有会话接口机械替换成 Muse 接口。
第一版目标是稳定的逐轮语音助手。自然全双工、声学打断、完全脱离电脑的人脸跟踪作为后续研究项。当前仅完成方案和公开文档研究，未获得设备型号、固件版本、账号设备能力和实机日志，所有工期均为规划估计。

3. 硬件和使用假设
默认目标为官方 CoreS3 版 StackChan、ESP32-S3、带 PSRAM、串行双舵机底座。首次工作必须读取实际型号、Flash 大小、舵机型号和当前校准；Core2、SG90 DIY 版不直接套用配置。
开发主机默认为用户 Mac。日常使用优先让设备直接连接 Muse；可选辅助服务承担 TTS 密钥代理、诊断或人脸检测。局域网服务不等于必须在同一 Mac，后续可迁移常开小主机。供电和舵机动作时的电压稳定性需实测。
所需准备：USB 数据线、设备、稳定 Wi-Fi、Muse 手机应用的设备配对能力、自有 Gadget SDK token，以及选定 TTS 的凭据或本地模型。令牌由用户在本机输入，不写入对话或版本控制。

5. 推荐架构
```mermaid
flowchart TD
  U[用户语音与触摸] --> F[StackChan 固件]
  F <--> G[Muse Gadget 会话适配]
  G <--> M[用户现有 Muse]
  G --> R[回复与任务事件]
  R --> T[TTS 适配器]
  T --> A[音频播放与口型]
  R --> S[本地交互状态机]
  S --> E[表情与动作调度]
  C[可选人脸跟踪服务] --> E
  E --> F
  A --> F
```
模块为逻辑划分，不代表全部独立进程。优先采用设备直连官方 Gadget 会话，保留上游配对和加密。可选 TTS 代理仅接收需要合成的文字，不承担第二个 AI 大脑；是否经过代理由凭据保护、内存和音频兼容性实测决定。
与 Groki Bot 相同的原则：机器人动作与云端推理解耦。眨眼、跟踪纠偏、嘴部幅度和舵机插值均在本地连续运行；Muse 只发送高层意图。持续跟踪不逐帧调用 LLM。

TTS 首选先验证用户已有或可接受的中文服务；Fish Audio、ElevenLabs 或本地中文 TTS 均作为候选，实际模型、价格、许可证与接口在接入前查官方文档确认。第一版只实现一个真正通过验收的 provider，再加第二个，避免过早抽象。无需默认引入 OpenAI、LangChain、Agent SDK、数据库或云后端。
7. Muse 适配契约：先验证再承诺
定义内部接口，不虚构服务端 API：send_voice、send_text（如果支持）、on_reply、on_status、on_device_command、on_disconnect。具体通过现有 SDK 回调实现；无法取得的状态标记为 unknown，不伪造事件。
关键实验：
1. 发送一个语音问题，确认回复能与输入关联，记录完整事件顺序。
2. 在设备会话询问用户在 Muse 主端明确保存的非敏感偏好，确认共享上下文的范围。
3. 请求一个无外部写入的工具任务，确认设备会话是否可使用既有连接器、是否继承其审批流程。
4. 在手机端继续该话题，确认会话历史是否共享、是否另开线程。
5. 运行较长的只读任务，确认返回的是受理消息还是最终结果、断连后是否重放。
6. 测试文本是完整回复还是增量事件；没有增量时，不承诺边生成边朗读。
7. 停止本地播放后，检查能否取消上游生成。不能取消时明确保留后台任务状态。
若官方设备通道无法满足主 Agent 的核心需求，先记录证据并调整体验；不默认转向读取桌面登录凭据、私有 API 或浏览器自动化。
8. 音频链路与状态机
基线：按键开始→录制→提交→等待 Muse→接收文字→合成→播放→回待机。录音输入格式、采样率和编码严格按上游当前实现，不在计划中假定可任意修改。
交互状态：BOOT、PAIRING、IDLE、LISTENING、SUBMITTING、WAITING_REPLY、SYNTHESIZING、SPEAKING、MUTED、RECOVERING、ERROR。任务状态独立保存为 unknown/accepted/running/completed/failed；只有平台事件能驱动真实完成状态。
每轮携带内部 turn_id 和 generation。取消时递增 generation，丢弃旧合成与旧播放结果，防止上一轮声音突然插入下一轮。播放结束必须来自实际播放器回调，不能以 TTS HTTP 返回作为播放完成。
第一版半双工；播放时暂停录音或忽略唤醒，通过触摸停止。恢复录音应等待音频排空并清除残留。多轮续听、VAD、唤醒在基础稳定后加入。超长回复使用单独的口语简短偏好或朗读长度设置，不能擅自丢掉用户需要的任务结果。
TTS 支持超时、格式验证、有限重试、用户取消；只有确认尚未开始播放时才可重试，避免重复播报。密钥代理部署后使用访问令牌和网络范围限制；默认不暴露公网。原始录音和转写默认不持久保存。
9. 表情和动作系统
分三层：真实交互状态→可选情绪修饰→动画渲染。聆听、等待、说话、错误是确定性反馈；“开心”“害羞”等不能覆盖错误或静音提示。嘴部使用音频包络驱动，不必等待逐字音素对齐。
动作优先级：紧急停止/设备拾起 > 校准 > 用户明确指令 > 跟踪 > 情绪动作 > 待机动作。同一时刻只有一个模块写入舵机目标；所有目标经过范围、速度、加速度检查。跟踪叠加点头需经仲裁，防止两个循环互相拉扯。
每设备保存 yaw/pitch 零位与最小最大值；首次校准低速、小幅运动。连接恢复后不重放旧动作队列。拾起或姿态异常时停止新的转动；任何过热、电源或串行异常的应对都以硬件实际可观测能力为限，不假定存在电流传感器。
10. 跟踪方案
阶段 A：Mac 摄像头检测一个目标脸，输出归一化中心点；通过已验证的设备指令通道发送低频、有界头部目标。电脑和机器人位置不同，必须设置几何偏差/手动偏置；“脸在电脑画面中心”不直接等于“机器人看着脸”。
阶段 B：用 StackChan 自身摄像头，先证明稳定取帧，再加入检测。可先把帧交主机处理，最后评估设备本地检测。相机、触摸引脚复用、PSRAM、I2S DMA、LVGL、网络栈并发需实测。
控制算法：最大脸或最近历史位置关联、中心死区、低通平滑、转速上限、丢脸超时。默认不存储帧、不识别人名、不持续扫房；退出跟踪后缓慢回中。建议先以 2–5 Hz 检测作为实验目标，不承诺帧率。
11. 内部控制协议（拟议，并非 Muse 官方协议）
设备内采用有界事件队列。若引入主机链路，再实现版本化 JSON 控制帧，音频沿用上游路径；不额外开放一套未认证硬件接口。
{
  "protocol_version": 1,
  "type": "head.target",
  "request_id": "example-request",
  "turn_id": "example-turn",
  "generation": 2,
  "ttl_ms": 1000,
  "payload": {"yaw_deg": 10, "pitch_deg": 20, "source": "tracking"}
}
类型包括 face.state、head.target、gesture.play、audio.stop、config.patch、device.status。回复包含 request_id、accepted/rejected 和 reason。TTL 用接收端单调时钟衡量，不依赖跨设备墙上时间；过期、未知版本和越界命令拒绝执行。重连清空临时动作，不清除校准。保持与上游 stackchan.face/look 的适配兼容。

13. 开发阶段与决策关卡
估计为一名熟悉 ESP32 的开发者实际工作日，包含有限实机迭代，不是 AI 自动运行时长承诺；依赖下载安装、设备访问和云端问题会增加等待时间。

MVP 规划约 6–10 个工作日，日常可用版本约 3–6 周，取决于跟踪与平台事件接口。全双工单独立项，不包含在上述完成承诺中。
M1 是首个 go/no-go：若同一 Muse 的基础问答与必要个人能力无法通过官方设备通道使用，则暂停后续体验开发，提交限制证据；不做一个换模型的机器人来冒充用户的 Muse。

15. 验收指标与测试方法
以下是拟定目标，未达成前不宣称实现：
- MVP：固定安静环境下 20 轮中文问答至少 19 轮完成；包含正常回答、无结果、超时和一次断网恢复。将平台故障单列，同时保留总成功率。
- 本地交互：按键/触摸后可见反馈目标小于 150 ms；停止播放目标小于 300 ms，以实际输入事件到输出停止测量。
- 端到端：记录录音结束→提交确认→首个回复文字→TTS 首字节→首个可听音。M1 测出 P50/P95，再决定可接受门槛，不预先保证低延迟。
- TTS：首版优先完整文本合成；若支持分句，按序播放、不重复、不混轮，取消后旧结果不得重新播出。
- 舵机：无命令越界、无突然满幅动作、手动退出跟踪后不反向抢控制；校准值重启后保留。
- 唤醒：30 次唤醒记录检出率；至少 2 小时桌面背景音记录误唤醒；模型选择以该结果决定。
- 并发：持续播放、刷新表情、转头和网络传输时记录剩余内存、最低堆、复位原因和欠载；相机单独增加后重测。
- 稳定性：MVP 2 小时；候选版 8 小时；发布前 24 小时，不能出现未解释复位、持续内存下滑或失控动作。
- 故障：TTS 401/429/超时、Muse 掉线、Wi-Fi 中断、重启、重复事件、乱序回复、相机失效，均有可观察状态和可恢复路径。
桌面测试不能代替实机验收。测试报告区分“静态审查通过”“编译通过”“模拟器通过”“实机通过”。不得只凭一次 HTTP 200 宣称语音完成。
16. 风险、成本和维护
风险	应对
Muse 会话/任务接口变化	小型适配层、锁版本、能力探针和回归场景
云端等待时间较长	立即本地反馈、明确处理中；不伪造任务进度
相机导致音频掉帧/内存不足	小缓冲、限制帧率、分核与优先级调度实验；保留主机方案
舵机供电噪声进入麦克风	实测供电、录音时动作策略、降低运动幅度与速度
自唤醒与重复播报	半双工基线、turn generation、幂等与播放状态回调
中文显示缺字	CJK 字库子集与内存预算；不盲目嵌入完整大字体
TTS 服务费用	用实际每月字符/音频量和当时官方价格估算；设长度及预算上限
上游许可或素材限制	逐文件审查；保留 NOTICE；Groki 的受限表情素材不直接复制商用


成本模型：Muse 账号使用量 + TTS 字符/音频调用 + 可选 STT（仅自行转写时） + 可选常开主机电力。当前不虚构价格；M1 后采样 100 轮日常问答，再做月用量估算。
凭据分离：Muse SDK token 按官方设备设计处理；TTS 私钥尽量留主机安全存储；日志脱敏。默认不开公网端口，不持续保存音频和图像。升级前保留已知可用版本及配置备份。

18. ChatGPT Project 初始化内容
建议名称：MuseStack｜StackChan × Muse
建议说明：
开发个人使用的 StackChan × Muse 实体 AI 终端。以官方 Muse Gadget SDK 和 MuseChan 为基础，复用现有硬件能力；实现中文语音、屏幕表情、平滑舵机动作、唤醒与人脸跟踪。Muse 是现有个人 Agent，不使用另一模型冒充。先验证账号、会话和语音闭环，再扩展体验。

项目指令（可粘贴到 Project Instructions）：
使用中文沟通。以本开发计划和最新源码为依据，将事实、设计选择和待验证假设明确区分。每次更改先说明目标，再做范围内实现和适当验证。锁定上游 commit 与 ESP-IDF；优先复用现有驱动。不得把编译通过当成实机通过，不得承诺未经测量的延迟、语音打断或记忆共享。固件刷写前先核对硬件并保留可恢复备份。所有舵机指令经过校准、限位、速度限制与调度仲裁。凭据不写入聊天或 Git。保留上游许可证。默认执行可逆工程工作；涉及用户账号操作、外部权限或不可逆硬件设置时按实际需要处理。记录 ADR、能力实验、测试结果和未解决问题；每轮结束说明完成项、验证和下一步。

首个实施任务：
从 M0 和 M1 开始。先检查工作区及适用的 AGENTS.md，读取本计划。盘点设备和主机环境；审计 MuseChan 与官方 Gadget SDK 的实际代码并锁定 commit。生成源码模块图和能力实验清单，识别真实的音频输入、文字输出、TTS hook、设备命令和重连路径。完成不依赖设备的构建准备。设备连接后先备份，再进行最小配对与语音→文字探针。M1 通过前不扩展唤醒、跟踪或复杂 UI；提供证据明确能否接入用户已有 Muse 的个人能力。

项目创建状态：本文件不代表 ChatGPT Project 已创建。当前自动化接口无新建 ChatGPT Project 功能，且应用 UI 自动操作被拒绝；需要用户在应用中手动新建，再加入本文件及以上指令。之后可继续在该项目开展开发。
