# Mac TLS 透传中继（开发环境）

设备的 Wi-Fi 不会继承 Mac 或手机的代理。若路由器没有可用的海外网络路径，可临时让 Mac 为设备转发 Muse 连接。Mac 必须保持运行、连接相同局域网，并能自行访问 Muse；本方案不会自动调用桌面代理的 HTTP 端口。

`companion/tls_relay.py` 仅接受指定设备 IPv4，绑定一个明确的私有局域网 IPv4，分别把 18443、18444 转发至固定的 `api.muse.ai:443`、`hatch.metaaivm.com:443`。不接受客户端提供的目标地址，不绑定所有网卡，不记录传输内容。每端口最多 6 个连接，有连接、背压和空闲超时。

TLS 在设备与官方服务之间建立。固件只改变 TCP 目的地，保留官方域名的 SNI、证书链和域名校验；中继不持有证书或解密内容。账户 API 保留原 Host，并在中继模式拒绝重定向。仅精确匹配两个固定官方域名，其他已配置服务继续直连。

本机私有配置的 `network.tls_relay_host` 填 Mac 局域网 IPv4；使用构建工具的 `--with-relay` 参数启用。默认配置为空、保持直连。不要把账号配置或含账号的固件上传仓库。

启动示例（地址需换成自己的，设备地址可从本机私有状态记录读取）：

```sh
.venv/bin/python -m companion.tls_relay --bind 192.168.1.5 --client 192.168.1.20
```

设备或 Mac 的 DHCP 地址变化后，需要重新核对配置。停止服务会使设备连接断开，但不会清除配对；恢复网络后按重连机制重试。后续若采用支持设备出网的路由器，可移除此开发中继依赖。

测试包括双向不透明字节传输、拒绝其他来源、禁止通配/公网监听及固件精确域名匹配。仍须以设备实际 TLS 连接和 Muse 对话作为验收；主机测试成功不代表对话成功。
