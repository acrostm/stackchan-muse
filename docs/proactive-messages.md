# 主动消息与计划任务播报

状态：后台收件箱及提示音/TTS 已接入，注入通知曾在旧探针上播放；真实手机与任务事件仍未验收。新增勿扰/未读控制见 [通知勿扰与未读](notification-quiet.md)，新实现尚未刷写。

目标：Muse 主动发来的消息、计划任务结果及其他需要通知用户的新消息，也能到达 MuseStack。默认先响短提示音，再用豆包音色朗读最终正文，同时显示通知表情和字幕；不要求用户先向设备发起一次语音对话。

## 已确认的源码事实

固定版本的 `muse_chat_session.cpp` 长期使用 `POST /chat/subscribe` 订阅事件，支持 `message.assistant` 与消息增量完成事件。当前 `on_event()` 已有独立后台通知入口，空闲时接收最终 assistant 文本，并保留当前回合关联及取消消息过滤。候选 notification/task 事件分支仍需真实服务端事件验证；不能因代码识别某个事件名就宣称账号会投递该事件。

这些事实不证明服务端会向订阅者投递所有会话、计划任务或主动消息。必须在账号配对后观察真实事件，确定会话范围、来源字段、完成信号、消息 ID、重放/断线语义，再逐项宣称支持。只记脱敏结构与计数，不把消息正文、录音、账号或设备身份放入日志和仓库。

## 首版行为

- 空闲时：收到符合范围、已完成且非空的新消息，提示音一次，再朗读并显示表情、字幕。
- 正在录音、思考或说话时：有界排队，优先完成当前交互，避免叠加音频；用户按停止后，旧通知不自行恢复。
- 勿扰或关闭播报时：保留未读提示，用户主动打开后再读；音量与开关尊重设备设置。
- 用稳定消息 ID 去重；只有实际播放完才记为已播报。处理中、失败和取消分别记录状态，不能把收到事件或 HTTP 200 当作播放成功。
- 只读最终正文，过滤工具内部事件及中间增量。超长消息按完整 UTF-8 字符分段，有总时长和队列上限。
- 断线或重启后不集中朗读历史消息；只有服务端已验证的游标/重放能力才能用作补偿，过期消息显示未读摘要。
- 网络和会话错误只影响通知通道，不能夺走触摸停止、正常对话和动作安全控制。

## 接入顺序与验收

1. 先完成无舵机探针的 Muse 配对和事件观察，分别测试设备语音回复、手机端新消息、Muse 主动消息、计划任务结果。
2. 每类记录是否实际到达、会话/关联字段和完成事件。若某类不由官方订阅流投递，明确标为不支持；仅评估官方提供的额外通知接口，不假设隐藏接口或读取手机通知作为通用方案。
3. 加入独立收件箱、去重/过期策略和统一音频调度，复用修复后的豆包 TTS 路径。
4. 逐类验证短提示音、朗读完成、字幕、静音、勿扰、触摸打断、断线、重放、重复事件、长文本、队列满和重启。

此需求纳入主线开发，但不能代替基本语音闭环、TTS 取消保护、头部校准及原有实机验收。
